GitHub 公开预览 Issue 状态与仓库看板，并可与代理自动化联动

GitHub 于 11 月 23 日在官方更新说明中宣布，Issue 状态和仓库看板进入公开预览。开发者可以在「未完成 / 已关闭」之外，用更细的状态跟踪进度，并在仓库内存视图里以看板方式查看和拖拽更新；这些状态也可通过接口和 MCP 供自动化与代理读写。

2026-11-24 开发者工具

GitHub 官方更新说明把这条功能的日期写在 2026 年 11 月 23 日。以往一个 Issue 多半只有打开或关闭两种结果，并不能说明它正在排队、正在做，还是已经送去审查。新的状态可以直接写在 Issue 上，创建时就能选，也可以事后在标题栏改。目前提供的状态包括：待办堆积、待处理、进行中、审查中、已完成、暂不计划和重复项。列表页、工作台和仓库看板上都会显示相应图标，还可以用 status: 过滤器查找。

为了减少手工改状态，GitHub 加了一组自动规则。把草稿拉取请求关联到 Issue，会把它标成进行中；把草稿标为待审查，或关联一个已打开的拉取请求，会改成审查中；把 Issue 指派给某个人，会改成待处理；指派给代理，则改成进行中。如果 GitHub 项目里的状态值和 Issue 状态对得上，两边改一处，另一处也会跟着变。这些规则的目的，是让人和代理对「现在进行到哪一步」有一份共同的记录，而不必再靠评论区里的口头同步。

同一天开放预览的，还有仓库看板。仓库里已有的保存视图可以改成看板布局，按状态分列，用拖拽改状态，不必离开仓库再跳到单独的项目管理工具。列、泳道、可见字段和排序都可以配置。GitHub 自己也划了边界：需要更完整规划能力时，仍应使用 GitHub 项目。另一项相关调整是，Issue 字段不再必须先绑定到某种 Issue 类型才能显示，可以在侧栏里直接添加；默认显示哪些字段，则仍然由类型上的固定设置决定。

对自动化来说，更关键的是接口已经打开。更新说明写明，GraphQL、REST API 和 MCP 服务都可以读取状态、修改状态，并在创建 Issue 时指定初始状态；状态变化也能作为 Copilot 自动化的触发条件。这意味着代理不仅可以被指派去处理某个 Issue，还可以把进度写回同一套状态里，供看板和后续规则使用。

这是公开预览，而不是已经默认对所有仓库生效的最终形态。状态名称、自动规则和看板布局都还可能调整，也不宜把它理解成可以完全取代 GitHub 项目。对已经在仓库里用 Issue 做日常协作的团队，这提供了一条更轻的进度视图；对主要依靠外部看板或自建工作流的团队，值得先看接口和自动规则能否对上现有流程，再决定要不要迁过去。

交叉核对

  • 一致处：功能要点、状态列表、自动规则、仓库看板以及 GraphQL / REST / MCP 支持，均直接来自 GitHub 2026 年 11 月 23 日官方更新说明，本窗口未见与之冲突的其他官方文档。
  • 范围：官方明确这是公开预览；需要更完整规划能力时，仍建议使用 GitHub 项目。
  • 待确认：预览期后是否默认对所有仓库开启、状态集合会否再改，更新说明中未给出时间表。
