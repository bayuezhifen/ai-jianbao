LiteLLM 1.107.0 供应链投毒：PyPI/Docker 恶意包约两小时下架

LiteLLM 官方确认 10 月 21 日发布管线被攻破，v1.107.0 轮子与若干 Docker 标签含窃凭据与远程加载逻辑；约两小时内从 PyPI 撤包。请钉 1.106.2 并轮换密钥。

2026-10-22 开发者工具

LiteLLM（常用 LLM 代理/路由库）10 月 21 日发布事故说明：当日清晨发布管线被攻破，向 PyPI 推送 litellm==1.107.0（七个 wheel，约世界时 11:39–13:23 在架），并向 Docker Hub / GHCR 推送带毒的 v1.107.0 以及曾指向同一脏索引的 latest、main-latest、main-stable 等标签。载荷会在 Python 启动时经 cook.pth / sitecustomize.py 等执行，窃取云、浏览器、开发者与 AI 相关凭据，并可加载远程代码。官方称此前版本安全，企业私有 registry 未受影响；GitHub 上的官方 1.107.0 源码标签并不含恶意文件，脏制品来自攻击者控制的仿造仓库。

官方复盘要点：攻击者拿到多枚开发者 GitHub CLI OAuth 凭据后，一度用组织所有者权限关掉分支保护并改发布工作流，把构建源指到 Berri-AI/litellm（注意连字符）仿造仓，再走 Trusted Publisher 签发。团队怀疑凭据来自内部 LiteLLM 部署日志里被写入响应体的 GitHub CLI token。处置建议：不要在已中招环境里直接 pip；先删 site-packages 里的 cook.* 与 sitecustomize.py，杀掉相关守护进程，重建环境并钉 litellm==1.106.2，轮换实例角色、代理库里的供应商密钥、DATABASE_URL 等一切可能被读到的秘密。

Datadog、JFrog、Wiz 等安全研究同步跟进，时间线与官方大体一致。本条放在开发者工具栏，强调的是包管理/发布管线供应链，而不是应用层 CVE 编号本身。

边界：与同日 PHP 紧急安全版、GitLab 高危补丁分列；不把「AI 写代码导致泄 token」扩写成对某一 IDE 的点名指控——官方只写到观察到 Claude Code 在特定情形把 GitHub CLI OAuth 写入响应体、若响应被记日志则可能曝光。

交叉核对

  • 多方一致：官方事故文与 Datadog/JFrog/Wiz 均确认 1.107.0 短窗投毒、已撤包、钉 1.106.2。
  • 分歧：攻击链中「内部部署如何被进」官方仍标为调查中；第三方文对恶意文件名细节略有出入，以官方清单为准。
  • 待确认：完整 IoC 与 CloudTrail 排查手册后续更新；是否还有未被官方点名的镜像标签。
