OpenAI 公布 Performance Factory，用 Codex 自动排查并修复性能回退

OpenAI 19 日撰文介绍内部系统 Performance Factory：在性能告警响起后，由 Codex 智能体自动调查回退、提出修复，并在上线后复查是否回到基线，工程师仍负责审阅。

2026-11-20 OpenAI

OpenAI 19 日在官网发表技术文章，介绍一套名为 Performance Factory 的内部系统。文章作者是技术员工 Okay Zed 与 Cyrus Forbes。他们写到，智能体开发的节奏已经让传统的性能工程方式难以跟上，于是公司用 Codex 和自有模型，搭起一条在云端自动调查并处理性能问题的流水线，以便继续推进产品路线图，同时把 ChatGPT 的响应速度维持住。

目前已经跑起来的第一条流水线，叫做回归工作流。性能告警触发后，系统会自动开出任务；一个智能体去调查变慢的原因，把发现写进任务，并给出一份供工程师审阅的修复建议。修复上线之后，另一个智能体再接手同一项任务，检查性能是否回到原先的基线。文章说，从调查、撰写修复到验证缓解，这条工作流已经把处理回退的过程从头到尾自动化了。在刚过三个月的时间里，它跟踪了 1700 多次调查，并在其中 600 多起里定位到根因，相当于每天约 17 次自动调查。

文章把这条路写成一个逐步放手的过程：早先工程师要自己盯指标、查日志、做性能剖析，后来可以让 Codex 当搭档一起查；再往后，团队把排查步骤收成名为 perf-forensics 的可复用技能，告警几乎只要贴进 Codex，就能得到一份诊断。再往后，调查被搬到云端自动启动，结果发到 Slack，但修复和复查仍要人来做。Performance Factory 要解决的，正是告警堆积之后，连哪些回退值得先看都要在对话线程里翻找的问题。作者也提醒，这是把已有的调查方法交给智能体去执行，而不是把最终合并代码的决定交给模型自己做。

需要说清楚界限。这是一篇面向工程实践的内部系统介绍，不是 ChatGPT 的新功能上线，也不是对外提供的性能产品。文中给出的 1700 次、600 起根因，都是公司自己统计的工作量，外界难以复核。截至本报截稿，尚未看到其他实验室用对等口径公布类似流水线的对比结果。它说明的是：OpenAI 已经把 Codex 用到自己的线上服务运维里，而且仍然把工程师的审阅留在关键节点上。

交叉核对

  • 一致处：OpenAI 官方博客写明回归工作流的步骤、工程师审阅修复，以及三个多月内 1700 多次调查、600 多起定位到根因、约每天 17 次自动调查。VentureBeat 等转述与官网数字相符。
  • 定位：这是内部工程系统的介绍，不是面向用户的新模型或新产品发布，官网与转述稿均未把它写成 ChatGPT 功能更新。
  • 待确认：修复建议被工程师采纳的比例、误报多少，以及是否会把这套方法对外提供，文章没有给出。
