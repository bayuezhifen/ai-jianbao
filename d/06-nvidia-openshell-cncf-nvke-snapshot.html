英伟达在 KubeCon 向 CNCF 捐赠 OpenShell，并发布 NVKE 与 Snapshot 预览

OpenShell 是面向自主智能体的安全与治理运行时，以沙箱项目进入基金会。同日还以 Apache 2.0 公开预览 DSX 平台组件：用来在 GPU 上运营托管 Kubernetes 的 NVKE，以及对已完成初始化的 GPU 任务做检查点、数秒到数十秒恢复的 Snapshot。官方写明尚不建议用于生产。

2026-11-10 英伟达 / NVIDIA

英伟达今天在 KubeCon 期间宣布，将开源运行时 NVIDIA OpenShell 捐赠给云原生计算基金会（CNCF），用于为自主智能体提供安全和治理，并以沙箱项目进入基金会。沙箱是基金会里较早的孵化阶段，并不等于项目已经成熟或被广泛部署。CNCF 同日发文欢迎这一捐赠，称 OpenShell 将采用基金会已有项目 Cedar 作为策略语言；早期贡献者包括英伟达、Red Hat、Docker 和 Canonical，代码仓库计划迁到中立组织 ai-openshell。Linux 基金会首席执行官吉姆·泽姆林表态支持由社区来治理 OpenShell。

英伟达还表示，将参与由谷歌发起、同样处于 CNCF 沙箱阶段的 Agent Substrate，以便在 Kubernetes 上运行长周期智能体，并与 Dynamo、KAI Scheduler 集成；双方正合作把 OpenShell 与 Agent Substrate 对接起来。这些都是治理和集成方向的宣布，并不等于相关能力已经在生产环境中普遍落地。

同一天，公司还以 Apache 2.0 许可证公开预览 DSX 人工智能工厂平台的若干开源组件，并写明尚不建议用于生产负载。其中，NVIDIA Kubernetes Engine（NVKE）与 NVIDIA Kubernetes Recipes（NVKR）用于在 GPU 基础设施上构建和运营托管的 Kubernetes。官方点名的合作或集成方包括 Firmus、SK Telecom，以及 Mirantis、Rafay、Spectro Cloud、OpenNebula Systems、vCluster 和 Netris。公开预览的含义是代码和文档已经放出，但官方自己也提醒，现阶段不要把它当成可以上生产的方案。

另一项是 NVIDIA Snapshot，用于对已经完成初始化的 GPU 任务做检查点并恢复，目的是避免每次都从冷启动重新准备环境。公司给出的基准是：恢复耗时 3.6 秒至 42.7 秒，相当于冷启动的 8 倍到 36 倍；约 600 GB 至 1 TB、跨越 8 块 GPU 的大型混合专家模型检查点可在 43 秒内恢复，而冷启动需要 6 到 19 分钟；生成检查点需要 15 秒到 5.5 分钟；并称「检查点生成时间加上恢复时间，仍短于一次冷启动」。设计合作伙伴 Crusoe 在 HGX B300 上运行 GLM-5.3 时，就绪时间从约 8 分钟降到 31 秒；Saturn Cloud 上的 vLLM 启动时间，分别从 2 分钟和 8.5 分钟降到 6 秒和 34 秒。上述数字均来自公司或合作伙伴提供的基准，不是独立复测。

把这几件事放在一起看，今天的主线是开源治理和基础设施软件，而不是新的训练芯片或机器人模型。OpenShell 进入的是沙箱阶段，策略语言选定 Cedar、仓库迁往中立组织，都还需要时间落地；NVKE、NVKR 和 Snapshot 虽然已经公开预览，官方却把「不建议用于生产」写得很清楚。检查点加速的数字也只说明在公司或合作伙伴的测试环境里，恢复可以短到数秒或数十秒，并不能直接外推到任意集群或任意工作负载。

交叉核对

  • 多方一致：英伟达博客与 CNCF 文章均确认 OpenShell 以沙箱项目进入基金会，定位是自主智能体的安全与治理运行时。NVKE、NVKR 和 Snapshot 以 Apache 2.0 公开预览，官方写明尚不建议用于生产。
  • 公司基准：Snapshot 的恢复时延、与冷启动的倍数比较，以及 Crusoe、Saturn Cloud 的例子，均来自官方或合作伙伴基准，本条未独立复核。
  • 待确认：仓库迁入 ai-openshell 的具体时间、与 Agent Substrate 的集成进度，以及这些预览组件何时适合生产，官方均未给出时间表。
