OpenAI 复盘周六故障：Postgres 副本维护失败，ChatGPT 与 API 错误率一度达75%

OpenAI 今天发布事故复盘称，11 月 21 日太平洋时间 1:48 至 5:21，一次 Postgres 只读副本维护导致两侧副本同时失效，付费和免费版 ChatGPT 的请求故障率一度达到 75%。

2026-11-22 OpenAI

OpenAI 在状态页发布了周六那场大面积故障的书面复盘。公司写道，11 月 21 日太平洋时间 1 时 48 分至 5 时 21 分（上海时间当天 17 时 48 分至 21 时 21 分），大量请求失败，付费和免费版 ChatGPT 的故障率一度达到 75%。事故持续约三个半小时。这不是模型本身的发布或功能更新，而是一次基础设施维护把身份认证这条公共路径打穿了。

直接原因写得很具体。维护针对的是主 API 服务所依赖的一套 Postgres 数据库，结果两个只读副本同时失效。OpenAI 解释说，虽然出问题的是副本而不是主库，但这些副本是承重的：主 API 服务承担用户认证和栈内服务之间的认证，依赖它们的请求路径随之失败。团队曾多次尝试救活原有副本，也尝试在其他地区拉起替代实例，都没有成功，最后是与服务商一起，在同一地区新开了两个副本，故障才被压住。

复盘里还写了已经做完和准备做的事。已经落地的包括：暂停同类维护、调整配置以减少连接抖动、增加可按比例把流量从副本切走的功能开关，并验证过把查询全部打到主库的假设。下一步则包括设立维护前审查、在维护窗口准备热备、保证关键服务所在地区有足够余量，以及为副本延迟失控准备短期自动恢复和长期架构改动。公司承认，这种量级的故障会直接伤到客户的产品和业务。

需要分开看的是：这次复盘解释的是周六晚上的故障，并不是今天又发生了新的宕机；OpenAI 官网新闻栏今天也没有新的产品稿。今早 08:20 的简报没有写这场周六傍晚的故障，故本窗按官方复盘补上。

从时间上说，故障开始于昨天下午简报发出之后，结束于今天凌晨之前，所以两期都没有赶上实时记录，只有今天这份复盘把原因和补救写清楚了。复盘也提醒了一个很普通、却容易被忽略的点：只读副本看起来像是可以从主库重建的附属品，但一旦认证、会话这类公共路径把它们当成承重构件，副本同时失效就会变成全站故障。OpenAI 自己也把这次归为“维护窗口不应演变成大面积停服”的问题，而不是一次来自外部的攻击。

交叉核对

  • 一致处：官方状态页复盘与后续技术转述都写明，故障窗口为 11 月 21 日太平洋时间 1:48–5:21，峰值故障率 75%，直接原因是 Postgres 只读副本在维护中同时失效，影响承担认证的主 API 服务。
  • 时区：11 月已结束夏令时，按太平洋标准时间 UTC−8 换算，对应上海时间 11 月 21 日 17:48–21:21，也就是昨天下午简报发布之后、今早简报之前。
  • 待确认：OpenAI 未点名该数据库的云服务商；也未公布受影响的具体请求量、各套餐之间的差异，以及是否有数据损坏。复盘聚焦可用性和恢复步骤。
